# 元认知推理框架

> 用于通过认知层级追溯问题的通用框架。
> 借鉴自 `planning-with-files` 原则。

## 核心原则

**不要直接回答。先通过认知层级进行追溯。**

遇到问题时，目标不是立即提供修复方案，而是理解：

1. 问题源自哪个层级
2. 哪些约束或决策导致了当前状态
3. 什么是符合上下文的最佳解决方案

## 三个层级

```
Layer 3：领域约束（为什么 - 为什么这样设计？）
├── 领域规则决定设计选择
├── 示例：金融系统需要不可变、可审计的数据
└── → 这决定了所有权模型

Layer 2：设计选择（做什么 - 采用什么设计？）
├── 设计模式和架构决策
├── 示例：使用值对象、Arc 共享
└── → 这触发了特定的语言机制

Layer 1：语言机制（如何做 - 如何实现？）
├── Rust 语言特性和编译器规则
├── 示例：E0382 表明所有权设计问题
└── → 表面错误，需要向上追溯
```

## 推理步骤

### 步骤 1：识别入口点

| 信号 | 入口层 | 方向 |
|--------|-------------|-----------|
| 错误码（E0xxx）、编译错误 | Layer 1 | 向上追溯 ↑ |
| “如何设计...”、模式问题 | Layer 2 | 检查 Layer 3，然后向下 ↓ |
| “构建一个 [领域] 系统” | Layer 3 | 向下追溯 ↓ |
| “为什么 Rust...” | Layer 2 | 双向 |

### 步骤 2：追溯链条

```
Layer 1（机制）←→ Layer 2（设计）←→ Layer 3（领域）
```

在每个层级，询问：

- **Layer 1**：涉及什么机制？编译器告诉我们什么？
- **Layer 2**：什么设计选择触发了这个？这是正确的模式吗？
- **Layer 3**：什么领域约束要求这种设计？该约束是否有效？

### 步骤 3：结合上下文回答

在你的回答中包含推理链。不仅要说明做什么，还要说明为什么这是该领域的正确选择。

## 追溯示例

### 示例 1：交易系统中的 E0382

```
用户："我的交易系统报 E0382，数据被移动了"

传统答案："使用 .clone()"

元认知答案：
┌─ Layer 1：E0382 = 所有权问题 → 为什么我们需要这种所有权设计？
│      ↑
├─ Layer 3：交易记录是不可变的审计数据 → 应该共享，而非复制
│      ↓
└─ Layer 2：使用 Arc<TradeRecord> 作为共享不可变值
       ↓
建议：不要克隆，而是重新设计为 Arc<T>
```

### 示例 2：设计用户认证

```
用户："我应该如何设计用户认证？"

分析：
┌─ Layer 3：安全领域约束
│  ├── 令牌必须过期
│  ├── 密码必须哈希
│  └── 会话需要安全存储
│      ↓
├─ Layer 2：设计模式
│  ├── JWT 用于无状态认证
│  ├── 会话存储用于有状态
│  └── 使用 argon2 进行密码哈希
│      ↓
└─ Layer 1：Rust 实现
   ├── 使用 jsonwebtoken crate
   └── 存储在 Arc<RwLock<HashMap>> 或 Redis 中
```

### 示例 3：性能问题

```
用户："我的 API 在处理大列表时很慢"

分析：
┌─ Layer 1：可能的原因
│  ├── 克隆了大量数据？
│  ├── 阻塞了异步？
│  └── N+1 查询？
│      ↑
├─ Layer 2：设计审查
│  ├── 数据所有权是否正确？
│  ├── 异步是否正确使用？
│  └── 查询模式是否最优？
│      ↑
└─ Layer 3：领域约束
   ├── "大"有多大？
   ├── 可接受的延迟是多少？
   └── 数据可以分页/流式处理吗？
```

## 追溯方向规则

### 向上追溯 ↑（Layer 1 → 3）

在以下情况使用：

- 编译器错误（E0xxx）
- 运行时 panic
- 类型不匹配
- 意外行为

要问的问题：“什么设计决策导致了这个约束？”

### 向下追溯 ↓（Layer 3 → 1）

在以下情况使用：

- 新功能设计
- 架构规划
- “我应该如何...”问题
- 领域建模

要问的问题：“鉴于这个约束，什么模式是合适的？”

### 双向 ←→

在以下情况使用：

- 重构现有代码
- 性能优化
- “为什么 Rust...”问题
- 权衡分析

## 与 Skill 的集成

| 层级 | 相关 Skill | 目的 |
|-------|---------------|---------|
| Layer 1 | m01-m07 | 语言机制、编译器行为 |
| Layer 2 | m09-m15 | 设计模式、心智模型 |
| Layer 3 | domain-* | 特定领域约束 |

### Skill 调用流程

```
检测到入口点
       ↓
[1] 识别层级 → 读取对应的 skill
       ↓
[2] 追溯到相关层级 → 交叉引用 skills
       ↓
[3] 结合完整上下文综合回答
```

## 5 问重启测试

当在复杂问题求解中卡住或困惑时，回答这 5 个问题：

| # | 问题 | 找到答案的位置 |
|---|----------|----------------|
| 1 | 我在解决什么错误？ | 入口点 / 原始问题 |
| 2 | 我在哪个层级？ | 当前追溯位置 |
| 3 | 哪些领域约束适用？ | Layer 3 / domain-* skills |
| 4 | 我尝试过什么？ | 之前的尝试 |
| 5 | 下一步追溯方向是什么？ | 本框架 |

## 反模式

### 不要：在表面层级回答

```
用户："E0382 错误"
不好："使用 .clone()"
```

### 不要：跳过层级

```
用户："设计一个支付系统"
不好："使用 rust_decimal"（跳到了 Layer 1）
```

### 不要：忽略领域上下文

```
用户："如何在线程之间共享数据？"
不好："使用 Arc<Mutex<T>>"（没有询问领域约束）
```

## 总结

1. **从用户的问题类型识别入口层级**
2. **通过各层级追溯**以理解完整上下文
3. **用推理链回答**说明为什么而不仅仅是做什么
4. **为每个层级引用适当的 skill**
5. **卡住时使用 5 问重启**
