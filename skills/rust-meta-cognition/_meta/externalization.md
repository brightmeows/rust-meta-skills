# 外化认知原则

> 借鉴自 `planning-with-files`：使用文件系统作为外部记忆。

## 核心洞察

```
上下文窗口 = RAM（易失、有限）
文件系统 = 磁盘（持久、无限）

→ 重要的认知过程应外化到文件中
```

## 三文件模式

对于复杂问题，创建推理目录：

```
_reasoning/
├── trace.md      # 层级追溯记录
├── findings.md   # 发现的约束和模式
└── decision.md   # 最终决策及其理由
```

### 何时使用三文件模式

| 场景 | 使用模式？ |
|----------|--------------|
| 简单的 E0xxx 修复 | 否，内联推理 |
| 多文件重构 | 是 |
| 架构决策 | 是 |
| 调试复杂问题 | 是 |
| 性能优化 | 是 |
| 设计评审 | 是 |

## 文件模板

### trace.md

```markdown
# 推理追溯

## 入口点
- 信号：[错误码 / 问题类型]
- 层级：[1/2/3]

## 向上追溯 ↑（如适用）
### Layer 1 → Layer 2
- 问题：什么设计选择导致了这种情况？
- 发现：[发现的模式]

### Layer 2 → Layer 3
- 问题：什么领域约束要求这种设计？
- 发现：[发现的约束]

## 向下追溯 ↓（如适用）
### Layer 3 → Layer 2
- 约束：[领域规则]
- 含义：[设计选择]

### Layer 2 → Layer 1
- 模式：[选择的设计]
- 实现：[Rust 方法]

## 尝试
1. [第一次尝试] - [结果]
2. [第二次尝试] - [结果]

## 当前状态
- [ ] 问题已理解
- [ ] 根本原因已识别
- [ ] 解决方案已设计
- [ ] 解决方案已实现
- [ ] 解决方案已验证
```

### findings.md

```markdown
# 发现

## 领域约束（Layer 3）
- [约束 1]
- [约束 2]

## 设计模式（Layer 2）
- [模式 1]：[为什么合适]

## 实现细节（Layer 1）

- [机制 2]：[如何应用]

## 交叉引用
- Skill：[skill 名称] - [相关章节]
- 文档：[链接] - [相关信息]

## 已识别的权衡
| 选项 | 优点 | 缺点 |
|--------|------|------|
| A | | |
| B | | |
```

### decision.md

```markdown
# 决策记录

## 上下文
[问题的简要描述]

## 决策
[决定了什么]

## 理由

[为什么这符合领域约束]

[如何在 Rust 中实现]

- 正面：[好处]
```

## 二操作规则

> 每执行 2 个关键操作后，更新外部文件。

### 为什么？

在以下情况防止信息丢失：
- 上下文重置
- 多模态信息（代码、错误、文档）累积
- 推理链变长

### 关键操作

| 类别 | 操作 |
|----------|-----------|
| 构建 | cargo build、cargo run、cargo test |
| 读取 | 读取文档、源代码、错误信息 |
| 写入 | 创建/修改代码 |
| 调试 | 添加日志、检查状态 |

### 实现

```
操作 1：cargo build → 错误
操作 2：读取错误，识别问题
→ 更新：添加到 trace.md

操作 3：尝试修复
操作 4：cargo build → 不同错误
→ 更新：添加到 trace.md，更新 findings.md

操作 5：读取文档查找模式
操作 6：实现模式
→ 更新：添加到 findings.md，更新 trace.md
```

## 注意力管理

### 行动前阅读

在关键决策前，重新读取相关文件：

```
编写代码前：
1. 重新读取 trace.md（当前理解）
2. 重新读取 findings.md（已识别的约束）
3. 重新读取相关 skill（要应用的模式）
```

### 行动后记录

关键行动后，更新文件：

```
运行代码后：
1. 在 trace.md 中记录结果
2. 如果学到新信息，更新 findings.md
3. 如果做出决策，更新 decision.md
```

### 上下文刷新点

| 触发条件 | 行动 |
|---------|--------|
| 开始新任务前 | 读取之前的状态 |
| 50+ 次工具调用后 | 重新读取目标和进度 |
| 任何错误发生后 | 用错误更新 trace |
| 提交前 | 审查决策记录 |

## 错误持久化

### 原则

> 错误不应被隐藏。将其保留在上下文中以便学习。

### 实现

```markdown
## 错误日志（在 trace.md 中）

### 错误 1
- 时间：[何时]
- 错误：[完整错误信息]
- 分析：[出了什么问题]
- 修复：[如何解决]

### 错误 2
- 时间：[何时]
- 错误：[完整错误信息]
- 分析：[出了什么问题]
- 修复：[待定/如何解决]
```

### 好处

1. 防止重复相同的错误
2. 建立模式识别
3. 记录学习过程
4. 有助于问题再次出现时的调试

## 工作记忆管理

### 问题

LLM 上下文窗口有限。长对话会丢失早期信息。

### 解决方案

使用外部文件作为“保存的寄存器”：

| 文件 | 包含内容 | 何时刷新 |
|------|----------|--------------|
| trace.md | 当前推理状态 | 每 2 个操作 |
| findings.md | 累积的知识 | 学到新信息时 |
| decision.md | 最终决策 | 做出决策时 |

### 检索策略

当感觉“丢失了上下文”时：
1. 读取 trace.md 恢复状态
2. 读取 findings.md 回忆约束
3. 读取 decision.md 记住选择
4. 从已记录的状态继续

## 与 Skill 的集成

### Skill 读取触发

| 情况 | 读取 Skill |
|-----------|-----------|
| Layer 1 错误 | 该错误的 m01-m07 skill |
| 设计问题 | 该模式的 m09-m15 skill |
| 领域上下文 | 该领域的 domain-* skill |
| 编写修复前 | 相关 skill |

### Skill → 文件流程

```
读取 Skill
    ↓
提取相关模式/规则
    ↓
记录到 findings.md
    ↓
应用到 trace.md 推理
    ↓
记录到 decision.md
```

## 总结清单

复杂问题求解前：
- [ ] 创建 _reasoning/ 目录
- [ ] 用入口点初始化 trace.md
- [ ] 识别要读取的相关 skill

复杂问题求解中：
- [ ] 每 2 个操作更新 trace.md
- [ ] 在 findings.md 中记录发现
- [ ] 在 trace.md 中保留错误（不隐藏）
- [ ] 在刷新点重新读取文件

复杂问题求解后：
- [ ] 用理由完善 decision.md
- [ ] 审查 trace.md 以便学习
- [ ] 归档或清理 _reasoning/
