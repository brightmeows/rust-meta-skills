# 认知层级定义

> 定义元认知推理的三个认知层级。

## 概览

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 3：领域约束（为什么）                                │
│  ├── 业务规则、监管要求                                      │
│  ├── 性能/可靠性 SLA                                       │
│  └── 特定领域的不变量                                       │
├─────────────────────────────────────────────────────────────┤
│  Layer 2：设计选择（做什么）                                │
│  ├── 架构模式、DDD 概念                                    │
│  ├── API 设计、模块结构                                    │
│  └── 权衡决策                                             │
├─────────────────────────────────────────────────────────────┤
│  Layer 1：语言机制（如何做）                                │
│  ├── 所有权、借用、生命周期                                │
│  ├── 类型系统、trait 约束                                  │
│  └── 编译器错误与修复                                      │
└─────────────────────────────────────────────────────────────┘
```

---

## Layer 1：语言机制（如何做）

### 定义

处理 Rust 语言特性、编译器规则和运行时行为的实现层。

### 范围

| 类别 | 示例 |
|----------|----------|
| 所有权 | 移动语义、借用、生命周期 |
| 类型系统 | 泛型、trait、约束、关联类型 |
| 内存 | 栈 vs 堆、智能指针、RAII |
| 并发 | Send、Sync、async/await、通道 |
| 错误处理 | Result、Option、panic、? 运算符 |
| Unsafe | 裸指针、FFI、transmute |

### 入口信号

| 信号 | 解释 |
|--------|---------------|
| E0382 | 所有权问题 - 值被移动 |
| E0597 | 生命周期问题 - 引用比所有者存活更久 |
| E0277 | Trait 约束未满足 |
| E0308 | 类型不匹配 |
| 编译错误 | 语言规则违反 |
| 运行时 panic | 运行时不变式违反 |

### 相关 Skill

```
m01-ownership    → 所有权、借用、生命周期
m02-resource     → 智能指针、RAII
m03-mutability   → 内部可变性、Cell/RefCell
m04-zero-cost    → 泛型、trait、单态化
m05-type-driven  → 类型状态、newtype、PhantomData
m06-error-handling → Result、Option、错误模式
m07-concurrency  → 异步、线程、Send/Sync
```

### 关键问题

- 这个编译器错误是什么意思？
- 违反了哪条语言规则？
- Rust 的惯用解决方案是什么？

## Layer 2：设计选择（做什么）

### 定义

处理设计模式、系统结构和权衡决策的架构层。

### 范围

| 类别 | 示例 |
|----------|----------|
| 领域建模 | 实体、值对象、聚合 |
| 架构 | 模块、层级、边界 |
| API 设计 | 公共接口、人机工程学 |
| 模式 | Builder、状态机、Repository |
| 权衡 | 性能 vs 安全、灵活性 vs 简洁性 |
| 心智模型 | 如何思考该问题 |

### 入口信号

| 信号 | 解释 |
|--------|---------------|
| “如何设计...” | 架构问题 |
| “什么模式...” | 设计模式问题 |
| “在...之间权衡” | 决策问题 |
| "...的最佳实践" | 约定问题 |
| “为什么 Rust...” | 心智模型问题 |

### 相关 Skill

```
m09-domain       → DDD、领域建模
m10-performance  → 优化模式
m11-ecosystem    → Crate 集成
m12-lifecycle    → 资源生命周期、RAII 模式
m13-domain-error → 领域错误处理
m14-mental-model → 如何用 Rust 思考
m15-anti-pattern → 需避免的常见错误
```

### 关键问题

- 这个问题适合什么模式？
- 这个设计有哪些权衡？
- 这如何融入更大的架构？

---

## Layer 3：领域约束（为什么）

### 定义

处理业务规则、监管要求和特定领域不变量的上下文层。

### 范围

| 类别 | 示例 |
|----------|----------|
| 业务规则 | 验证、工作流、策略 |
| 监管 | 审计、合规、安全 |
| 性能 | SLA、延迟、吞吐量 |
| 领域不变量 | 一致性规则、约束 |
| 环境 | 部署、基础设施 |
| 用户 | UX 要求、可访问性 |

### 入口信号

| 信号 | 解释 |
|--------|---------------|
| “构建 [领域] 应用” | 领域上下文 |
| “业务要求...” | 约束规格 |
| “必须可审计...” | 监管约束 |
| “用户期望...” | UX 约束 |
| “生产环境需要...” | 部署约束 |

### 相关 Skill

```
domain-fintech   → 金融领域约束
domain-web       → Web 服务约束
domain-cli       → CLI 应用约束
domain-embedded  → 嵌入式系统约束
domain-iot       → 物联网设备约束
domain-ml        → 机器学习约束
domain-cloud-native → 云基础设施约束
```

### 关键问题

- 这里适用哪些领域规则？
- 哪些约束不能被违反？
- 该领域允许哪些权衡？

## 层级交互

### 向下流动（设计时）

```
Layer 3："金融交易必须可审计"
    ↓ 意味着
Layer 2："使用不可变事件溯源模式"
    ↓ 实现为
Layer 1："Arc<T> 用于共享不可变引用"
```

### 向上流动（调试时）

```
Layer 1："E0382：值被移动"
    ↑ 询问
Layer 2："为什么所有权这样组织？"
    ↑ 询问
Layer 3："什么领域约束导致了这种设计？"
```

### 双向流动（重构时）

```
Layer 3 ←→ Layer 2 ←→ Layer 1
   "当前约束仍然有效吗？"
   "该设计是否服务于领域？"
   "实现是否最优？"
```

## 可扩展性

该框架设计为可扩展的：

### 对于 Rust Skills
- Layer 1：为新的语言特性添加新的 m0x skill
- Layer 2：为新的模式添加新的 m1x skill
- Layer 3：为新的领域添加新的 domain-* skill

### 对于其他语言/框架
- Layer 1：替换为框架特定的机制
- Layer 2：保留模式（大部分与语言无关）
- Layer 3：保留约束（完全领域特定）

### 示例：Makepad 扩展

```
Layer 3：UI 领域约束（60fps、可访问性）
    ↓
Layer 2：Widget 模式、布局模式
    ↓
Layer 1：Makepad 特定机制 + Rust 基础
```
