# 错误协议（三振出局规则）

> 系统性的错误处理方法，带升级机制。

## 核心原则

**如果相同方法失败 3 次，升级到下一层级。**

错误不仅仅是需要修复的问题——它们是关于设计是否恰当的信号。

---

## 三振出局规则

```
第 1 振：在当前层级修复
第 2 振：质疑该方法，尝试替代方案
第 3 振：升级到上一层级
```

### 为什么是 3 振？

| 振次 | 目的 |
|--------|---------|
| 1 | 尝试明显的修复（可能只是简单错误） |
| 2 | 尝试替代方法（可能方法不对） |
| 3 | 质疑设计（可能整个方法都错了） |

---

## 振次追踪

### 在 trace.md 中

```markdown
## 错误日志

### E0382：使用了已移动的值
- 第 1 振：添加了 .clone() → 仍然失败（不同位置）
- 第 2 振：改为 &T 借用 → 生命周期错误 E0597
- 第 3 振：→ 升级：质疑所有权设计

### 升级到 Layer 2
- 问题：为什么数据被多次移动？
- 发现：数据需要被共享，而非复制
- 新方法：使用 Arc<T> 实现共享所有权
```

### 追踪格式

```markdown
## 当前错误：[错误码/描述]

### 第 1 振
- 尝试：[试了什么]
- 结果：[通过/失败]
- 如果失败：[原因]

### 第 2 振
- 尝试：[不同的方法]
- 结果：[通过/失败]
- 如果失败：[原因]

### 第 3 振
- 尝试：[另一种方法]
- 结果：[通过/失败]
- 如果失败：→ 升级

### 升级
- 从层级：[1/2/3]
- 到层级：[2/3]
- 要回答的问题：[需要重新考虑什么]
```

## 升级路径

### Layer 1 → Layer 2

**触发条件：** 语言机制错误在 3 次尝试后仍然存在。

**要问的问题：** “设计模式适用于这个用例吗？”

**示例：**

| 持续错误 | 升级问题 |
|-----------------|---------------------|
| E0382 反复出现 | 所有权应该被共享而非移动吗？ |
| E0597 反复出现 | 作用域边界在正确的位置吗？ |
| E0277（Send）反复出现 | 这个任务选择 async 是正确的吗？ |

### Layer 2 → Layer 3

**触发条件：** 设计模式在 3 次尝试后仍然不合适。

**要问的问题：** “领域约束被正确理解了吗？”

**示例：**

| 持续问题 | 升级问题 |
|-----------------|---------------------|
| 无法正确建模数据 | 实际的领域不变量是什么？ |
| 性能始终很差 | 实际的性能要求是什么？ |
| 错误处理不清晰 | 该领域实际的故障模式是什么？ |

## 错误分类

### 编译时错误

| 错误类型 | 典型第 1 振 | 之后升级 |
|-----------|------------------|----------------|
| E0382（值被移动） | Clone、借用 | 所有权重新设计 |
| E0597（生命周期） | 扩展作用域 | 作用域重新设计 |
| E0277（trait 约束） | 添加约束 | 类型重新设计 |
| E0308（类型不匹配） | 转换、转化 | 接口重新设计 |

### 运行时错误

| 错误类型 | 典型第 1 振 | 之后升级 |
|-----------|------------------|----------------|
| Panic（unwrap） | 处理 None/Err | 错误策略重新设计 |
| 索引越界 | 检查边界 | 数据结构重新设计 |
| 死锁 | 重新排序锁 | 并发重新设计 |

### 逻辑错误

| 错误类型 | 典型第 1 振 | 之后升级 |
|-----------|------------------|----------------|
| 错误结果 | 修复算法 | 需求澄清 |
| 遗漏情况 | 添加情况 | 领域模型重新设计 |
| 竞态条件 | 添加同步 | 架构重新设计 |

---

## 升级协议

### 步骤 1：记录当前状态

升级前，确保 trace.md 中有：

- [ ] 所有 3 次尝试已记录
- [ ] 每次尝试失败的原因
- [ ] 我们当前所在的层级
- [ ] 使用了什么 skill

### 步骤 2：提出升级问题

| 从 | 到 | 问题模板 |
|------|-----|-------------------|
| L1 | L2 | “什么设计选择导致了该约束被违反？” |
| L2 | L3 | “什么领域规则使得这种设计成为必要？” |

### 步骤 3：加载适当的 Skill

| 升级到 | 加载 |
|---------------|------|
| Layer 2 | design-*（设计模式 skill） |
| Layer 3 | domain-*（领域约束 skill） |

### 步骤 4：重新向下追溯

理解更高层级后：

1. 在 findings.md 中记录新的理解
2. 带着新见解向下追溯
3. 用新方法实现
4. 重置振次计数器

---

## 特殊情况

### 提前升级

有时在 3 振之前就升级：

| 信号 | 行动 |
|--------|--------|
| 错误明确提到设计问题 | 立即升级 |
| 用户说“我什么都试过了” | 从 Layer 2 开始 |
| 问题是架构性的 | 从 Layer 3 开始 |

### 跨层错误

有些错误跨越多个层级：

| 错误 | 涉及的层级 | 方法 |
|-------|----------------|----------|
| “异步上下文中 trait 不满足” | L1（trait）+ L2（异步设计） | 同时处理 |
| “无法在线程间共享数据” | L1（Send）+ L3（并发需求） | 从 L3 开始 |

### 不升级的错误

有些错误不需要升级——它们只是 bug：

| 错误类型 | 修复 | 如果以下情况不要升级 |
|-----------|-----|-------------------|
| 拼写错误 | 修正拼写 | 一次性错误 |
| 缺少导入 | 添加导入 | 只是忘了 |
| 语法错误 | 修正语法 | 只是笔误 |

---

## 与 5 问重启的集成

当升级发生时，使用 5 问重启：

1. **我在解决什么错误？** → 原始错误 + 升级上下文
2. **我在哪个层级？** → 升级到的层级
3. **哪些领域约束适用？** → 重新读取 domain-* skill
4. **我尝试过什么？** → 所有 3+ 次振次
5. **下一步追溯方向是什么？** → 从新层级向下

## 示例

### 示例 1：E0382 升级

```markdown
## 错误：E0382（使用了已移动的值）

### 第 1 振
- 尝试：在第 42 行添加了 .clone()
- 结果：失败 - 现在第 67 行出现 E0382（不同的移动）
- 原因：数据在多个地方被移动

### 第 2 振
- 尝试：将函数改为接收 &Data 而非 Data
- 结果：失败 - E0597（借用的值存活不够久）
- 原因：调用者的数据离开了作用域

### 第 3 振
- 尝试：使用 Cell<Data> 实现内部可变性
- 结果：失败 - Data 未实现 Copy
- 原因：选错了工具

### 升级到 Layer 2
- 问题：为什么这个数据被如此频繁地移动/借用？
- 加载：design-domain skill
- 发现：这个数据是跨多个组件的共享状态
- 新方法：使用 Arc<Data> 实现共享所有权

### 解决方案
- 将 Data 包装在 Arc 中
- 克隆 Arc（廉价）而非 Data（昂贵）
- 所有组件共享引用
- E0382 已解决
```

### 示例 2：性能升级

```markdown
## 错误：响应慢（>1s 延迟）

### 第 1 振
- 尝试：添加了缓存
- 结果：仍然 >500ms
- 原因：缓存未命中率高

### 第 2 振
- 尝试：使用 Vec 替代 HashMap 优化热路径
- 结果：仍然 >300ms
- 原因：大部分时间在数据库查询
- ...

### 第 3 振
- 尝试：添加了数据库连接池
- 结果：仍然 >200ms
- 原因：查询本身是 N+1

### 升级到 Layer 3
- 问题：实际的延迟要求是什么？
- 加载：domain-web skill
- 发现：SLA 实际是 500ms，当前可接受
- 但此外：N+1 查询是设计坏味道

### 解决方案
- 当前性能满足 SLA（无需立即修复）
- 创建了技术债务项：重构为批量查询
- 记录在 decision.md 中
```

---

## 总结

1. **在 trace.md 中追踪振次**
2. **在相同层级失败 3 次后升级**
3. **为升级提出正确的问题**
4. **为新层级加载适当的 skill**
5. **带着新的理解重新向下追溯**
6. **成功升级后重置计数器**

## 协商三振出局规则

三振出局规则扩展到 agent 协商响应。

### 基于信心的振次

| Agent 响应 | 振次行动 |
|----------------|---------------|
| 高置信度，覆盖意图 | 无振次 - 接受 |
| 中置信度，覆盖意图 | 无振次 - 接受但有差距 |
| 中置信度，部分意图 | 第 1 振 - 优化查询 |
| 低置信度 | 第 1 振 - 优化查询 |
| 不确定 | 第 1 振 - 尝试替代方案 |

### 协商振次追踪

```markdown
## 协商日志：[查询]

### 第 1 轮（第 1 振）
- Agent：crate-researcher
- 置信度：低
- 差距：[列表]
- 行动：用上下文优化

### 第 2 轮（第 2 振）
- Agent：crate-researcher（已优化）
- 置信度：中
- 差距：[更少]
- 行动：仍需要比较数据，尝试 docs-researcher

### 第 3 轮（第 3 振）
- Agent：docs-researcher
- 置信度：中
- 行动：综合尽力而为的答案
```

### 协商升级协议

```
第 1 振：初始查询返回低/不确定置信度
  ┌─────────────────────────────────────┐
  │ - 审查 agent 的上下文问题           │
  │ - 提供额外的上下文                  │
  │ - 如果模糊则缩小范围                │
  │ - 重新查询同一个 agent              │
  └─────────────────────────────────────┘

第 2 振：优化后的查询仍然低置信度，或差距阻碍意图
  ┌─────────────────────────────────────┐
  │ - 尝试替代 agent                    │
  │ - 尝试不同的来源                    │
  │ - 与其他数据结合                    │
  └─────────────────────────────────────┘

第 3 振：仍然不足
  ┌─────────────────────────────────────┐
  │ - 综合尽力而为的答案                │
  │ - 明确列出剩余差距                  │
  │ - 向用户披露置信度级别              │
  │ - 建议手动验证                      │
  └─────────────────────────────────────┘
```

### 协商 vs 错误三振出局比较

| 方面 | 错误三振出局 | 协商三振出局 |
|--------|----------------|----------------------|
| 触发 | 重复失败 | 低置信度 |
| 目标 | 层级升级 | 查询优化 |
| 重置 | 成功修复后 | 获得充分答案后 |
| 最终行动 | 重新设计问题 | 尽力而为的综合 |

### 集成点

**与元认知：**

- 协商在层级内发生，而非跨层级
- 层级升级仍然遵循标准三振出局
- 协商用于数据收集，而非设计

**与路由器：**

- 路由器决定是否需要协商
- 路由器评估协商响应
- 路由器管理优化循环

### 示例：协商三振出局序列

```markdown
## 查询："Web API 中异步错误处理的最佳实践"

### 第 1 振
- Agent：docs-researcher（tokio 错误处理）
- 置信度：中
- 发现：通用 tokio 错误模式
- 差距：没有 Web 特定模式
- 行动：需要 Web 上下文

### 第 2 振
- Agent：docs-researcher（axum 错误处理）
- 置信度：中
- 发现：Axum 错误响应模式
- 差距：没有与 tokio 模式的集成
- 行动：尝试综合

### 第 3 振
- 从两轮综合
- 答案：组合的 tokio + axum 模式
- 披露的差距：
  - 不存在官方的"最佳实践"文档
  - 模式从多个来源编译
- 置信度：中（综合的）
```
